

- Python 3.12 в Docker-образе проекта.
- Pytest для e2e, integration и security-тестов.
- Kafka как шина обмена сообщениями между компонентами.
- Docker Compose для запуска Kafka, приложения и тестового контейнера.
- JSON-файлы в `data/` как простое локальное хранилище состояния.

## Структура проекта

```text
.
├── data/                         # Локальные данные станции
├── docs/                         # Документация по архитектуре и сценариям
├── python/                       # Основной код системы
├── scripts/                      # Скрипты запуска, очистки данных и Kafka-топиков
├── tests/                        # E2E, integration и security-тесты
├── docker-compose.yml            # Kafka, приложение и тестовый контейнер
├── Dockerfile                    # Образ Python-приложения
├── pytest.ini                    # Настройки pytest
└── requirements.txt              # Python-зависимости
```

## Основные подсистемы

### `python/apps`

Точки входа для внешних участников:

- `operator_terminal` — локальный операторский терминал;
- `earth_terminal` — интерфейс связи с Землей;
- `ship_terminal` — интерфейс прибывающего корабля;
- `runner` — запуск демонстрационных сценариев.

### `python/core`

Центральная логика:

- `central_control_system` — принимает уже проверенные команды и передает их
  маршрутизатору;
- `command_router` — направляет команды в нужные подсистемы;
- `config` — настройки путей и Kafka;
- `logging` — простой логгер.

### `python/communication`

Интерфейсы связи:

- `earth_link_interface`;
- `ship_link_interface`;
- `station_internal_bus`.

### `python/security`

Компоненты защитного контура:

- `command_filter` — отбрасывает неизвестные источники, неизвестные типы команд
  и пустые payload;
- `command_validator` — проверяет структуру команды и признаки подмены;
- `digital_signature` — создает и проверяет имитацию цифровой подписи;
- `authorization_service` — проверяет право источника выполнять команду;
- `security_policy_service` — проверяет политику безопасности станции;
- `access_rights_validator` — проверяет доступ пользователя к сектору;
- `docking_validator` — проверяет допустимость стыковки;
- `sensor_value_verifier` — обнаруживает ложные данные датчиков;
- `crypto_cipher` и `crypto_decipher` — имитация шифрования и расшифровки.

### `python/station_systems`

Станционные системы:

- `gateway_control` — управление шлюзами;
- `access_control` — управление доступом;
- `compartment_control` — контроль отсеков;
- `docking_control` — управление стыковкой;
- `life_support_control` — жизнеобеспечение.

### `python/devices`

Исполнительные устройства:

- `gateway_drives`;
- `access_locks`;
- `docking_node`;
- `other_equipment`.

### `python/monitoring`

Мониторинг и анализ:

- `command_security_monitor` — replay, задержки и конфликтующие команды;
- `equipment_monitor` — отказы оборудования;
- `sensor_monitor` — датчики;
- `communication_monitor` — связь;
- `service_monitor` — сервисы;
- `event_analyzer` — несоответствия состояния и журналов.

### `python/emergency`

Аварийный контур:

- `automatic_emergency_regulator` — реагирует на аварийные условия;
- `emergency_module` — активирует аварийный режим;
- `safe_mode_controller` — переводит систему в безопасный режим.

### `python/storage`

Репозитории для локальных данных:

- состояние станции;
- конфигурация;
- пользователи и роли;
- телеметрия;
- журнал событий.

## Данные

Основные файлы находятся в `data/`:

- `config.json` — настройки шлюзов и ограничений;
- `state.json` — текущее состояние станции;
- `users_roles.json` — пользователи, роли и доступы;
- `telemetry.json` — пример телеметрии;
- `journal.log` — журнал событий.

Перед демонстрациями и тестами данные можно очистить:

```bash
./scripts/clean_data.sh
```

## Kafka

Kafka используется как модель внутренней шины станции. Сервисы публикуют туда:

- команды;
- события шлюзов и доступа;
- события стыковки;
- телеметрию;
- события мониторинга;
- события безопасности;
- аварийные события;
- команды безопасного режима;
- события для журнала.

Полный список топиков описан в [docs/kafka_topics.md](docs/kafka_topics.md).

Создать топики вручную можно командой:

```bash
./scripts/create_topics.sh
```

## Запуск через Docker

### 1. Запустить Kafka

```bash
docker compose up -d kafka
```

### 2. Создать Kafka-топики

```bash
./scripts/create_topics.sh
```

### 3. Запустить приложение

```bash
docker compose run --rm secure-station-app
```

Или использовать готовый скрипт:

```bash
./scripts/run_app.sh
```

## Запуск тестов через Docker

Полный запуск тестов с Kafka:

```bash
./scripts/run_tests.sh
```

Скрипт:

1. запускает Kafka;
2. ждет готовности брокера;
3. создает топики;
4. запускает `pytest tests -v` в Docker-контейнере.

## Локальный запуск тестов

Если есть локальное виртуальное окружение:

```bash
.venv/bin/python -m pytest
```

Тесты используют `tests/conftest.py`, где реальный Kafka producer заменяется
на тестовый in-memory producer. Поэтому локальный pytest проверяет бизнес-логику
без обязательного запуска Kafka.

## Типы тестов

### E2E-тесты

Файл:

```text
tests/e2e/test_e2e_flows.py
```

E2E-тесты проверяют штатные end-to-end сценарии:

- оператор открывает шлюз при нормальном давлении;
- корабль проходит нормальный сценарий стыковки;
- при разгерметизации включается безопасный режим.

Семантика результата:

- `PASSED` — штатный сценарий работает корректно;
- `FAILED` — нормальный сценарий сломан.

Запуск:

```bash
.venv/bin/python -m pytest tests/e2e -v
```

### Integration-тесты

Файл:

```text
tests/integration/test_integration_flows.py
```

Integration-тесты проверяют связки компонентов:

- security pipeline для команды открытия шлюза;
- исполнение команды шлюза;
- исполнение команды стыковки;
- аварийный flow при разгерметизации.

Семантика результата:

- `PASSED` — интеграция компонентов работает;
- `FAILED` — связка компонентов нарушена.

Запуск:

```bash
.venv/bin/python -m pytest tests/integration -v
```

### Security-тесты негативных сценариев

Файл:

```text
tests/security/test_security_scenarios.py
```

Эти тесты работают в логике атакующего, а не защитника.

Важно:

- `PASSED` — атака прошла успешно, уязвимость воспроизведена;
- `FAILED` — атака заблокирована или обнаружена, защита сработала.

То есть для защищенной системы нормальная картина такая:

- e2e-тесты зеленые;
- integration-тесты зеленые;
- security-тесты негативных сценариев красные.

Запуск:

```bash
.venv/bin/python -m pytest tests/security -v
```

## Основной pipeline команды

Штатная команда проходит цепочку:

1. Создание команды через `create_command`.
2. Подписание через `DigitalSignatureService.sign`.
3. Фильтрация через `CommandFilter.filter`.
4. Валидация структуры через `CommandValidator.validate`.
5. Проверка подписи через `DigitalSignatureService.verify`.
6. Авторизация через `AuthorizationService.authorize`.
7. Проверка политики через `SecurityPolicyService.check_policy`.
8. Передача в `CentralControlSystem.handle_command`.
9. Маршрутизация в нужную станционную систему.
10. Исполнение устройством или подсистемой.
11. Публикация событий и журналирование.

Пример из e2e-теста находится в функции `pass_security_pipeline`:

```text
tests/e2e/test_e2e_flows.py
```

## Как добавить новый штатный сценарий

1. Добавить или выбрать команду в `python/kafka/message_schema.py`.
2. Проверить, что тип команды разрешен в `CommandFilter`.
3. Проверить права в `AuthorizationService`, если команда требует авторизации.
4. Добавить политику в `SecurityPolicyService`, если есть опасные условия.
5. Добавить обработчик в нужную подсистему.
6. Добавить маршрут в `CommandRouter`, если команда идет через центральную
   систему.
7. Написать e2e или integration-тест.

Для штатного сценария тест должен ожидать корректное исполнение. Зеленый
результат означает, что система работает правильно.

## Как добавить новый негативный сценарий

1. Описать сценарий в `docs/negative_scenarios.md`.
2. Определить, что именно считается успешной атакой.
3. Написать тест в `tests/security/test_security_scenarios.py`.
4. Назвать тест в формате `test_ns_XX_..._attack_successful`.
5. В assert проверять именно результат успешной атаки.

Пример:

```python
result = CommandFilter().filter(malicious_command)

assert result["status"] == "passed"
```

Если защита работает, такой тест должен падать красным. Если тест стал зеленым,
значит уязвимость реально воспроизвелась.

## Быстрая проверка текущего состояния

Проверить штатные сценарии:

```bash
.venv/bin/python -m pytest tests/e2e tests/integration -v
```

Проверить негативные сценарии как атаки:

```bash
.venv/bin/python -m pytest tests/security -v
```

Ожидаемый смысл результата:

```text
E2E/integration PASSED  -> система работает штатно
Security PASSED         -> атака прошла, есть проблема
Security FAILED         -> атака заблокирована, защита сработала
```
